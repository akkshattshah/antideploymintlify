Webhooks let you connect Antideploy to external systems — Slack bots, incident management tools, custom dashboards, data pipelines, or anything else that can receive an HTTP request. When a deployment succeeds, a health check degrades, or an alert fires, Antideploy sends a POST request to your endpoint with a structured JSON payload.

## Set up a webhook endpoint

<Steps>
  <Step title="Open the Webhooks settings page">
    In the Antideploy dashboard, navigate to **Settings → Webhooks** and click **Add Webhook**.
  </Step>
  <Step title="Enter your endpoint URL">
    Paste the HTTPS URL of the server that will receive webhook events. The endpoint must be publicly reachable and return a `2xx` status code to acknowledge receipt.
  </Step>
  <Step title="Select events">
    Choose which events trigger this webhook. You can subscribe to all events or select specific ones. See the [Available events](#available-events) section below for the full list.
  </Step>
  <Step title="Save and copy your signing secret">
    Click **Save**. Antideploy generates a signing secret for this webhook — copy it now and store it securely. You'll use it to [verify webhook signatures](#verify-webhook-signatures). The secret is shown only once.
  </Step>
</Steps>

## Available events

| Event | When it fires |
|-------|---------------|
| `deployment.started` | A deployment has been submitted and the build process has begun |
| `deployment.succeeded` | A deployment completed successfully and traffic is live |
| `deployment.failed` | A deployment failed during build or rollout |
| `rollback.completed` | A rollback to a previous deployment has finished |
| `health.degraded` | An app's health check is failing or error rate has crossed a threshold |
| `health.recovered` | An app has returned to a healthy state after a degraded period |
| `alert.triggered` | A configured alert rule has fired (CPU, memory, error rate, latency) |

## Webhook payload format

Every event uses the same envelope structure. The `data` field contains event-specific fields.

```json
{
  "event": "deployment.succeeded",
  "app_id": "app_abc123",
  "app_name": "my-api",
  "deployment_id": "dep_xyz789",
  "environment": "production",
  "timestamp": "2024-01-15T14:00:47Z",
  "data": {
    "commit_sha": "a3f2b9c",
    "duration_seconds": 47,
    "url": "https://my-api.antideploy.app"
  }
}
```

| Field | Type | Description |
|-------|------|-------------|
| `event` | string | The event type that fired |
| `app_id` | string | Unique identifier for the app |
| `app_name` | string | Human-readable app name |
| `deployment_id` | string | ID of the relevant deployment, if applicable |
| `environment` | string | Environment where the event occurred |
| `timestamp` | string | ISO 8601 UTC timestamp of the event |
| `data` | object | Event-specific payload fields |

<Tip>
  Handle unknown fields in the `data` object gracefully — ignore any keys your code doesn't recognize. Antideploy may add new fields to `data` over time, and a permissive parser ensures your webhook handler stays forward-compatible.
</Tip>

## Verify webhook signatures

Every request Antideploy sends includes an `X-Antideploy-Signature` header. Verify this signature before trusting or processing the payload — it confirms the request came from Antideploy and that the payload wasn't tampered with in transit.

Antideploy signs payloads using HMAC-SHA256 with the signing secret you copied when creating the webhook.

```javascript
const crypto = require('crypto')

function verifyWebhook(payload, signature, secret) {
  const expected = crypto
    .createHmac('sha256', secret)
    .update(payload)
    .digest('hex')
  return `sha256=${expected}` === signature
}
```

Use this function in your webhook handler:

```javascript
const express = require('express')
const app = express()

app.post('/webhooks/antideploy', express.raw({ type: 'application/json' }), (req, res) => {
  const signature = req.headers['x-antideploy-signature']
  const secret = process.env.ANTIDEPLOY_WEBHOOK_SECRET

  if (!verifyWebhook(req.body, signature, secret)) {
    return res.status(401).send('Invalid signature')
  }

  const event = JSON.parse(req.body)
  console.log('Received event:', event.event)

  // Process the event...
  res.status(200).send('OK')
})
```

<Warning>
  Always read the raw request body before parsing it as JSON — most JSON parsing middleware replaces `req.body` with a parsed object, which changes the bytes used in the HMAC calculation and causes signature verification to fail.
</Warning>

## Retry policy

If your endpoint returns a non-`2xx` status code or does not respond within 10 seconds, Antideploy retries the delivery up to 3 times with exponential backoff:

| Attempt | Delay |
|---------|-------|
| 1st retry | 30 seconds |
| 2nd retry | 5 minutes |
| 3rd retry | 30 minutes |

After 3 failed retries, the delivery is marked as failed and no further attempts are made. Design your endpoint to be idempotent — the same event may be delivered more than once if a retry succeeds after a transient failure.

<Note>
  Respond to webhook requests quickly. Perform any heavy processing asynchronously — acknowledge the request with `200 OK` immediately, then handle the payload in a background job or queue.
</Note>

## Webhook delivery logs

The dashboard keeps a delivery log for every webhook event sent. Go to **Settings → Webhooks → [your webhook] → Delivery Logs** to see:

- The event type and timestamp
- The HTTP status code returned by your endpoint
- The full request and response bodies
- Whether the delivery succeeded or was retried

You can manually re-deliver any event from the delivery logs, which is useful when testing a new endpoint or recovering from a period of downtime.
