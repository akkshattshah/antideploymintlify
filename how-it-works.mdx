When you give Antideploy your code — through GitHub, the CLI, or a ZIP upload — it doesn't ask you to fill out a form describing your application. Instead, it reads your code directly and figures out everything it needs to know: what your app is, what it depends on, what infrastructure it requires, and how to build and run it. This page explains exactly what happens at each stage.

## The Deployment Lifecycle

<Steps>
  <Step title="Code Ingestion">
    Antideploy receives your source code — either as a repository push, a CLI upload, or a ZIP archive. It indexes every file in your project to prepare for analysis. No files are ignored by default; the full project is available to the analysis engine.
  </Step>
  <Step title="Code Analysis">
    The analysis engine reads your project to identify:

    - **Language and runtime** — detected from file extensions, runtime configuration files (`.nvmrc`, `.python-version`, `go.mod`, `Gemfile`), and lock files
    - **Framework** — identified from package manifests, directory structure, config files, and entry points
    - **Build system** — detected from `package.json` scripts, `Makefile`, `pyproject.toml`, and similar files
    - **Entry points** — the server process(es) Antideploy needs to start after the build
    - **Environment variables** — discovered from `.env.example`, `dotenv` usage, and config loading patterns (values are never read, only key names)
    - **Dependencies** — catalogued from lock files to ensure a reproducible build environment

    <Note>
      Antideploy never reads the values of secrets or environment variables from your code — only the names, so it can prompt you to supply them before the first deployment.
    </Note>
  </Step>
  <Step title="Infrastructure Inference">
    Based on analysis results, Antideploy determines exactly what infrastructure your application needs. This inference is specific to your stack — not a one-size-fits-all template.

    See [Infrastructure Inference Examples](#infrastructure-inference-examples) below for a breakdown of what gets provisioned for common stacks.
  </Step>
  <Step title="Infrastructure Provisioning">
    Antideploy provisions all required infrastructure in parallel before your build starts:

    - Compute instances are sized based on framework and detected workload type
    - PostgreSQL databases are created with credentials injected automatically as environment variables
    - Object storage buckets are created and configured with the appropriate access policies
    - Queues and worker processes are set up from job definitions in your code
    - Cron jobs are registered from scheduler configuration
    - Networking, load balancing, and internal DNS are configured automatically

    Provisioning typically completes in 15–30 seconds. You never write a single line of infrastructure configuration.
  </Step>
  <Step title="Build Execution">
    Antideploy runs your build pipeline in an isolated, reproducible environment:

    1. **Dependencies installed** — using the package manager and lock file from your project (`npm ci`, `pip install`, `bundle install`, etc.)
    2. **Build command executed** — the detected or configured build command runs (`npm run build`, `python manage.py collectstatic`, etc.)
    3. **Artifact packaging** — build outputs are collected and prepared for deployment
    4. **Image creation** — a minimal runtime image is assembled from your build artifacts

    Build logs stream in real time to the dashboard and CLI.
  </Step>
  <Step title="Deployment">
    Antideploy deploys your application using a zero-downtime rollout:

    - The new version starts alongside the existing version (if one exists)
    - Health checks confirm the new version is responding correctly
    - Traffic shifts to the new version incrementally
    - The previous version is kept on standby for instant rollback

    Your application is never unavailable during a deployment.
  </Step>
  <Step title="Post-Deploy Activation">
    Immediately after a successful deployment, Antideploy activates the full operations stack:

    - **SSL certificate** — issued via Let's Encrypt and attached to your deployment URL
    - **Domain assignment** — your app receives a `*.antideploy.app` subdomain; custom domains can be added at any time
    - **Health monitoring** — uptime checks begin immediately, with configurable alert thresholds
    - **Log aggregation** — runtime logs are collected and indexed for search
    - **Metrics collection** — request rate, latency, error rate, and resource utilization are tracked continuously
    - **App Intelligence activation** — the intelligence layer ingests your deployment context and begins monitoring for anomalies
  </Step>
  <Step title="Continuous Operations">
    After deployment, Antideploy continues to manage your application:

    - **Auto-scaling** — compute scales up under load and back down during quiet periods
    - **Automatic restarts** — crashed processes are restarted immediately with backoff logic
    - **Database maintenance** — automated backups, connection pooling, and version patch management
    - **Certificate renewal** — SSL certificates are renewed automatically before expiry
    - **Dependency vulnerability scanning** — your dependency tree is monitored for known CVEs
  </Step>
</Steps>

## Infrastructure Inference Examples

Antideploy infers infrastructure requirements from your actual code — not from a template you fill out. Here are examples of what gets provisioned for common stacks:

| Stack Detected | Automatically Provisioned |
|---|---|
| **Next.js** | Compute (Node.js), CDN for static assets, edge routing |
| **Next.js + Prisma** | Compute, CDN, PostgreSQL, connection pooler |
| **Django + Postgres ORM** | Compute (Python), PostgreSQL, static file storage |
| **Django + Celery** | Compute, PostgreSQL, Redis queue, worker processes |
| **Express.js API** | Compute (Node.js), optional PostgreSQL if ORM detected |
| **FastAPI** | Compute (Python), PostgreSQL if SQLAlchemy detected |
| **Laravel** | Compute (PHP-FPM), PostgreSQL or MySQL, Redis, storage |
| **Rails** | Compute (Ruby), PostgreSQL, Active Storage bucket |
| **Nuxt.js** | Compute (Node.js), CDN, SSR edge routing |
| **SvelteKit** | Compute (Node.js), CDN, adapter-auto routing |
| **Go HTTP server** | Compute (Go binary), PostgreSQL if `database/sql` detected |
| **Static site (any)** | CDN-only deployment, no compute provisioned |

<Tip>
  Antideploy detects dozens of additional frameworks and languages beyond this table. If your stack isn't listed, it will likely still be detected correctly — and if anything is missed, you can override any setting in the dashboard or via `antideploy.json`.
</Tip>

## The App Intelligence Layer

App Intelligence is Antideploy's context-aware operations layer. Unlike generic monitoring tools, App Intelligence knows your specific stack, your dependency versions, your database schema, and your deployment history.

When an issue occurs, App Intelligence:

- **Identifies the root cause** — correlating logs, metrics, and code context rather than showing you raw stack traces
- **Explains the issue in plain language** — written for developers, not for SREs
- **Suggests a fix** — based on your actual code and known solutions for your framework and version
- **Tracks recurrence** — alerts you if the same issue reappears across deployments

<Note>
  App Intelligence activates automatically after your first successful deployment. No configuration, no instrumentation code, and no SDK to install.
</Note>

## Zero Cloud Knowledge Required

Antideploy is designed so that you never need to understand the underlying cloud infrastructure. You don't need to know what instance type your app is running on, which availability zone your database lives in, or how your load balancer is configured. All of those decisions are made automatically and adjusted over time.

If you do want to customize infrastructure — to specify minimum instance counts, set resource limits, or configure advanced networking — you can do that through the dashboard or an `antideploy.json` file in your repository. But it's always optional, and the defaults work for the vast majority of applications.
