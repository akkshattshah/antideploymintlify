Antideploy monitors your application from the moment you deploy. Every app gets a live metrics dashboard, automatic health checks, and a fully configurable alert system — no third-party setup required.

## What Antideploy monitors automatically

As soon as your app goes live, Antideploy begins collecting the following signals without any code changes:

<CardGroup cols={2}>
  <Card title="Request Rate" icon="chart-line">
    Requests per second, broken down by endpoint and HTTP method.
  </Card>
  <Card title="Latency" icon="clock">
    P50, P95, and P99 response times across all requests.
  </Card>
  <Card title="Error Rate" icon="triangle-exclamation">
    Percentage of 4xx and 5xx responses over rolling time windows.
  </Card>
  <Card title="CPU Usage" icon="microchip">
    Per-instance CPU utilization, averaged and per-peak.
  </Card>
  <Card title="Memory" icon="server">
    Heap and resident memory usage over time, with OOM detection.
  </Card>
  <Card title="Database Connections" icon="database">
    Active, idle, and waiting connections to attached databases.
  </Card>
</CardGroup>

All metrics are retained for 30 days by default and are queryable across any time range within that window.

## The Metrics dashboard

Open the **Metrics** tab inside any app in the Antideploy control center to see a real-time view of all collected signals. The dashboard lets you:

- Select a custom time range (last 15 minutes to 30 days)
- Compare metrics across deployments to spot regressions
- Overlay deployment events on the timeline to correlate changes with metric shifts

<Tip>
  Pin your most important charts to the top of the dashboard using the **⭐ Pin** button on any chart tile. Pinned charts load first every time you open Metrics.
</Tip>

## Health checks

Antideploy continuously pings your application to confirm it is accepting traffic and responding correctly. By default, it sends an HTTP `GET` request to `/` every 30 seconds and expects a `2xx` response within 5 seconds.

### Failure behavior

<Steps>
  <Step title="First failure detected">
    Antideploy marks the instance as unhealthy and stops routing new traffic to it while continuing to probe.
  </Step>
  <Step title="Three consecutive failures">
    The unhealthy instance is automatically restarted. Traffic continues flowing to healthy instances during the restart.
  </Step>
  <Step title="Instance comes back">
    A single failed check is treated as noise; repeated failures mark the app as down.
  </Step>
</Steps>

<Warning>
  If **all** instances fail their health checks simultaneously, Antideploy keeps the last known-good instance running and triggers a critical alert rather than taking your app fully offline.
</Warning>

### Setting up a custom health check endpoint

A dedicated health endpoint gives you more control than the default `/` check — you can verify database connectivity, cache availability, or any other dependency.

```javascript
// Express example
app.get('/health', async (req, res) => {
  try {
    await db.query('SELECT 1');
    res.status(200).json({ status: 'ok', db: 'connected' });
  } catch (err) {
    res.status(503).json({ status: 'error', db: 'unavailable' });
  }
});
```

## Alerts

Antideploy lets you define threshold-based alerts on any monitored metric. When a threshold is breached, notifications are sent through your configured channels.

### Configuring alert thresholds

Navigate to **Settings → Alerts** in the control center, or define alerts in `antideploy.yaml`:


### Alert severity levels

| Severity | Color | Use for |
|---|---|---|
| `critical` | 🔴 Red | Downtime, error spikes, complete health failure |
| `warning` | 🟡 Yellow | Elevated latency, approaching resource limits |
| `info` | 🔵 Blue | Deployment events, recovery notices |
