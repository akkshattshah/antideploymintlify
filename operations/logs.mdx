Antideploy captures every line your application writes to `stdout` and `stderr` the moment it starts running. No log agents, sidecars, or SDK integrations are required — your logs appear in the dashboard and CLI immediately after your first deployment.

## How logs are captured

Antideploy collects log output from two sources:

- **Standard streams** — anything your app writes to `stdout` or `stderr` is captured verbatim.
- **Structured logs** — JSON objects written to `stdout` are parsed automatically, making their fields available as searchable metadata (level, request ID, user ID, and so on).

Logs from all instances running your app are merged into a single unified stream, with each line tagged by instance ID and environment.

## Viewing logs in the dashboard

Open the **Logs** tab inside any app in the Antideploy control center to see a live, scrolling view of your application output.

<Steps>
  <Step title="Select your environment">
    Use the environment switcher at the top of the Logs tab to choose **production**, **staging**, or a specific preview deployment.
  </Step>
  <Step title="Enable live tail">
    Toggle **Follow** to stream new log lines in real time as your app produces them. New lines appear at the bottom of the view automatically.
  </Step>
  <Step title="Pause and inspect">
    Click anywhere in the log list to pause live tail. Scroll up freely to inspect earlier output, then click **Resume** to jump back to the present.
  </Step>
</Steps>

## Searching and filtering logs

Use the filter bar above the log list to narrow results:

<CardGroup cols={2}>
  <Card title="By log level" icon="layer-group">
    Show only `error`, `warn`, `info`, or `debug` lines using the **Level** dropdown.
  </Card>
  <Card title="By time range" icon="calendar">
    Pick a preset window (last 15 min, 1 h, 24 h, 7 d) or set a custom start and end time.
  </Card>
  <Card title="By text" icon="magnifying-glass">
    Enter any string in the search box. Antideploy highlights matches and hides non-matching lines.
  </Card>
  <Card title="By instance" icon="server">
    Filter to a specific instance ID — useful when debugging a problem on one node in a multi-instance deployment.
  </Card>
</CardGroup>

<Tip>
  Use structured JSON logging (see [below](#structured-json-logging)) to make filters like `level:error AND userId:usr_abc123` possible directly in the dashboard.
</Tip>

## Log levels

Antideploy recognizes four standard log levels. When your app emits structured JSON, Antideploy reads the `level` field and applies color coding automatically:

| Level | Color | When to use |
|---|---|---|
| `error` | 🔴 Red | Unhandled exceptions, failed operations that affect users |
| `warn` | 🟡 Yellow | Recoverable issues, deprecated usage, unexpected but non-fatal states |
| `info` | ⚪ White | Normal operational events — requests, jobs started, config loaded |
| `debug` | 🔵 Blue | Verbose detail useful during development; typically filtered out in production |

<Note>
  `debug` logs are captured in all environments but hidden by default in the dashboard filter. Enable them explicitly when troubleshooting.
</Note>

## Tailing logs from the CLI

Use the `antideploy logs` command to stream or query logs without leaving your terminal:

```bash
# Stream live logs for an app
antideploy logs --app my-app

# Follow logs in real time (tail mode)
antideploy logs --app my-app --follow

# Show only error-level logs from the past hour
antideploy logs --app my-app --level error --since 1h
```

Available flags:

| Flag | Description |
|---|---|
| `--follow` | Stream new log lines in real time (tail mode) |
| `--level <level>` | Filter to a specific log level: `error`, `warn`, `info`, or `debug` |
| `--since <duration>` | Show logs from the past `1h`, `30m`, `2d`, etc. |

## Log retention

<Tabs>
  <Tab title="Default policy">
    Antideploy retains all logs for **7 days** on the Starter plan and **30 days** on the Pro and Team plans. Logs older than the retention window are permanently deleted.
  </Tab>
  <Tab title="Extended retention">
    Upgrade your retention window under **Settings → Logs → Retention**. Extended retention options (90 days, 1 year) are available on the Team and Enterprise plans.

    ```yaml
    # antideploy.yaml
    logs:
      retention_days: 90
    ```
  </Tab>
</Tabs>

<Warning>
  Logs cannot be recovered after the retention window expires. Export or archive important logs before they age out.
</Warning>

## Structured JSON logging

Plain-text logs are fine, but structured logs unlock the full power of Antideploy's search and filter tooling. Emit a JSON object per line and Antideploy will parse it automatically.

<CodeGroup>
```javascript Node.js (pino)
import pino from 'pino';

const log = pino(); // writes JSON to stdout by default

log.info({ userId: 'usr_abc123', action: 'login' }, 'User logged in');
log.error({ err, requestId: req.id }, 'Payment failed');
```

```python Python (structlog)
import structlog

log = structlog.get_logger()

log.info("user_logged_in", user_id="usr_abc123", action="login")
log.error("payment_failed", error=str(e), request_id=request_id)
```

```go Go (zerolog)
import "github.com/rs/zerolog/log"

log.Info().
    Str("userId", "usr_abc123").
    Str("action", "login").
    Msg("User logged in")
```
</CodeGroup>

The JSON output Antideploy expects:

```json
{
  "level": "info",
  "time": "2025-01-15T10:32:00.000Z",
  "msg": "User logged in",
  "userId": "usr_abc123",
  "requestId": "req_xyz789"
}
```

Any top-level field in the JSON object becomes a filterable attribute in the dashboard. Fields like `requestId`, `userId`, or `traceId` let you reconstruct the full sequence of events for a single user or request in seconds.
