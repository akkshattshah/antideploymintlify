Environments let you run multiple isolated versions of your application under one project. Production serves your live users. Staging gives you a safe place to validate changes before they go live. Preview environments spin up automatically for every pull request. Each environment gets its own URL, its own set of environment variables and secrets, and its own dedicated infrastructure — changes in one environment never affect another.

---

## Environment types

| Environment | Purpose | URL pattern | Lifecycle |
|---|---|---|---|
| **Production** | Serves live user traffic | `yourapp.antideploy.app` | Permanent |
| **Staging** | Pre-production validation | `yourapp-staging.antideploy.app` | Permanent |
| **Preview** | Per-pull-request testing | `yourapp-pr-42.antideploy.app` | Deleted on PR close |

Every project starts with a **production** environment. You create staging and any additional environments yourself.

<Note>
  Preview environments are only available for projects connected to a [GitHub repository](/deploying/github). They are created automatically when a pull request is opened and torn down when it is closed or merged.
</Note>

## Create a staging environment

<Tabs>
  <Tab title="Dashboard">
    1. Open your project in the Antideploy dashboard.
    2. Click **Environments** in the left sidebar.
    3. Click **New Environment**.
    4. Enter a name (e.g., `staging`) and choose a region.
    5. Select a **source branch** if you want auto-deploys from a specific branch (e.g., `dev`).
    6. Click **Create Environment**.

    Antideploy provisions dedicated infrastructure for the new environment immediately. The staging URL is available within seconds.
  </Tab>
  <Tab title="CLI">
    ```bash
    # Create a staging environment
    antideploy env create staging

    # Create a staging environment in a specific region
    antideploy env create staging --region us-east

    # List all environments for the current project
    antideploy env list
    ```

    After creation, deploy to your new environment:

    ```bash
    antideploy deploy --env staging
    ```
  </Tab>
</Tabs>

## Promote staging to production

The promote workflow lets you take a deployment that has already been built and tested in staging and activate it in production — without rebuilding. The exact same artifact that passed your staging validation goes live.

<Tabs>
  <Tab title="Dashboard">
    1. Open your project and navigate to **Environments → Staging**.
    2. Find the deployment you want to promote in the **Deployments** list.
    3. Click the **⋯** menu on that deployment and select **Promote to Production**.
    4. Review the summary — it shows the deployment ID, commit SHA, and build timestamp.
    5. Click **Confirm Promotion**.

    Traffic shifts to the promoted deployment instantly. The previous production deployment remains available for rollback.

    <Tip>
      Enable **Promotion approval** in **Settings → Environments** to require a second team member to approve every production promotion.
    </Tip>
  </Tab>
  <Tab title="CLI">
    ```bash
    # Promote the latest staging deployment to production
    antideploy promote --from staging --to production

    # Promote a specific deployment by ID
    antideploy promote dep_7rNp1w --to production

    # Preview what will be promoted without making changes
    antideploy promote --from staging --to production --dry-run
    ```

    The CLI prints a summary of what will change and asks for confirmation before promoting. Pass `--yes` to skip the prompt in automated pipelines.

    ```bash
    antideploy promote --from staging --to production --yes
    ```
  </Tab>
</Tabs>

## Environment variables and secrets

Each environment maintains its own set of environment variables. A variable set on staging is not visible to production, and vice versa.

<Tabs>
  <Tab title="Dashboard">
    1. Navigate to **Environments → [Environment name] → Variables**.
    2. Click **Add Variable**.
    3. Enter the key and value.
    4. Toggle **Secret** to encrypt the value — secrets are write-only after saving and never shown in plaintext again.
    5. Click **Save**. The variable takes effect on the next deployment.

    To apply the new variable immediately without a full redeploy, click **Restart** on the current deployment.
  </Tab>
  <Tab title="CLI">
    ```bash
    # Set a variable on staging
    antideploy env set DATABASE_URL postgres://... --env staging

    # Set a secret (encrypted, write-only)
    antideploy env set STRIPE_SECRET_KEY sk_live_... --env production --secret

    # List all variables for an environment (secrets shown as ***)
    antideploy env vars --env staging

    # Remove a variable
    antideploy env unset DATABASE_URL --env staging
    ```
  </Tab>
</Tabs>

<Warning>
  Never put secrets directly in your source code or `antideploy.json`. Always use environment variables so credentials are never stored in version control.
</Warning>

## Preview environments for pull requests

When your project is connected to GitHub, Antideploy automatically creates a preview environment for every pull request targeting your production branch.

Preview environments:
- Inherit environment variables from staging by default (configurable under **Settings → Previews**)
- Receive the same build pipeline as production
- Get a unique URL posted as a comment on the pull request
- Are destroyed automatically when the pull request is closed or merged
- Can be promoted directly to production without a rebuild

To disable preview environments for a project, go to **Settings → Previews** and toggle **Automatic preview deployments** off.

## Copy configuration between environments

To bootstrap a new environment with the same variables as an existing one:

<Tabs>
  <Tab title="Dashboard">
    1. Navigate to **Environments → [Source environment] → Variables**.
    2. Click **⋯ → Copy to environment**.
    3. Select the target environment and click **Copy**. Existing variables in the target are not overwritten unless you check **Overwrite existing**.
  </Tab>
  <Tab title="CLI">
    ```bash
    # Copy all variables from staging to a new environment
    antideploy env copy --from staging --to preview-manual

    # Copy and overwrite any existing variables in the target
    antideploy env copy --from staging --to preview-manual --overwrite
    ```
  </Tab>
</Tabs>

<Note>
  Secret values are not copied between environments for security reasons. After copying, set any required secrets directly on the target environment.
</Note>

## Delete an environment

Deleting an environment permanently destroys all associated deployments, infrastructure, and variables. This cannot be undone.

<Tabs>
  <Tab title="Dashboard">
    Navigate to **Environments → [Environment name] → Settings** and click **Delete Environment**. Type the environment name to confirm.
  </Tab>
  <Tab title="CLI">
    ```bash
    antideploy env delete staging
    ```

    The CLI prompts you to confirm by typing the environment name before deleting.
  </Tab>
</Tabs>

<Warning>
  You cannot delete the **production** environment. To decommission a project entirely, delete the project from **Project Settings → Danger Zone**.
</Warning>
