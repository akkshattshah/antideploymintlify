Environment variables let you configure your application's behavior without touching your codebase. Use them to set database URLs, toggle feature flags, define API endpoints, or pass any non-sensitive configuration your app needs at runtime.

<Note>
  Environment variables are not the right place for sensitive credentials like API keys, tokens, or passwords. Use [Secrets](/configuration/secrets) instead — they are encrypted at rest and never displayed in plain text after saving.
</Note>

## Setting variables from the dashboard

Open your app in the control center, navigate to **Configuration → Environment Variables**, and click **Add Variable**. Enter the key and value, choose which environment the variable applies to, and click **Save**. Changes take effect on the next deployment unless live reload is enabled for that variable.

## Setting variables from the CLI

<CodeGroup>
```bash Set a single variable
antideploy env set DATABASE_URL=postgres://user:pass@host:5432/mydb --app my-app
```

```bash Set multiple variables from a file
antideploy env set --file .env --app my-app
```

```bash Get a single variable's value
antideploy env get MY_VAR --app my-app
```

```bash List all variables
antideploy env list --app my-app
```

```bash Remove a variable
antideploy env unset MY_VAR --app my-app
```
</CodeGroup>

Add `--env production` or `--env staging` to any of these commands to target a specific environment. Without the flag, the command applies to your default environment.

## Environment-specific variables

Each app in Antideploy can have separate variable sets for **production** and **staging** (and any additional environments you create). This lets you point your staging app at a test database while production uses the live one — with the same codebase.

To manage environment-specific variables:

<Steps>
  <Step title="Select your environment">
    Use the **Environment** dropdown at the top of the Environment Variables panel to switch between production, staging, and any custom environments.
  </Step>
  <Step title="Set the variable">
    Add or update variables in the selected environment. Values set here override any global variables with the same key.
  </Step>
  <Step title="Deploy to apply">
    Trigger a new deployment to roll out the updated configuration to that environment.
  </Step>
</Steps>

## Variables injected automatically by Antideploy

Antideploy injects a set of variables into every deployment automatically. You do not need to set these yourself:

| Variable | Description |
|---|---|
| `DATABASE_URL` | Connection string for your provisioned database |
| `STORAGE_URL` | Base URL for your provisioned object storage bucket |
| `REDIS_URL` | Connection string for your provisioned Redis instance (if enabled) |
| `ANTIDEPLOY_APP_ID` | The unique ID of your app |
| `ANTIDEPLOY_ENV` | The current environment name (`production`, `staging`, etc.) |
| `ANTIDEPLOY_DEPLOY_ID` | The ID of the current deployment |

If you set a variable with the same name as an automatically injected one, your value takes precedence.

## When changes take effect

| Change type | When it applies |
|---|---|
| New variable added | Next deployment |
| Variable value updated | Next deployment (or immediately if live reload is enabled) |
| Variable removed | Next deployment |

**Live reload** is available for a subset of variables that Antideploy can inject at runtime without a full redeploy — for example, feature flags and non-connection-string config values. Enable live reload per-variable from the dashboard by toggling **Live Reload** when editing the variable.

<Tip>
  Use a `.env.example` file in your repository to document which variables your app expects. Your team members and future deployments will thank you.
</Tip>
